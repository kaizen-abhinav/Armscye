## 0. Instructions for the builder

Build the smallest working version of the product described below. Prioritize a complete end-to-end demo over feature breadth.

1. **Inspect the current repository before making changes.** Reuse a working setup where possible; do not overwrite existing code or configuration blindly.
2. Implement the core experience in this order: **catalogue → customer photo → FASHN try-on → switch garments → catalogue-based recommendations**.
3. Use the open-source **FASHN VTON v1.5** project for virtual try-on. Do not replace it with generic OpenAI image generation as the primary try-on engine.
4. Keep the VTON model behind a separate service/adapter so its runtime can be moved to a compatible GPU host without rewriting the frontend.
5. If hardware, dependencies, or model weights prevent local inference, report the exact blocker and finish the rest of the product flow. Do not fake a successful AI result or silently substitute an unrelated generated image.
6. Keep secrets on the backend. Never expose API keys in client code, commit them, or log them.
7. Do not implement 360-degree reconstruction, measurements, size guarantees, payment, accounts, or WhatsApp in this MVP.
8. Update the README with setup instructions, environment variables, model/license attributions, limitations, and a demo flow.

## 1. Product summary

MirrorFit AI is a tablet-friendly web application for Indian clothing stores. A customer selects a garment from the store's real catalogue, uploads or captures a full-body photo, and receives a virtual try-on image generated by FASHN VTON v1.5. The customer can try additional garments and browse recommendations drawn only from the store's catalogue.

### Primary value proposition

Help customers preview how a garment might look on them before they physically try it on. Help retailers make their existing products easier to explore.

### MVP success definition

A judge can complete the following journey without developer intervention:

1. Open a populated clothing catalogue.
2. Upload or capture a customer photo.
3. Select a supported garment and tap **Try On**.
4. See a real FASHN-generated result.
5. Select another garment and generate another result without uploading the person photo again.
6. Browse relevant alternatives from the real catalogue.

The core technical milestone is one reasonably faithful front-facing try-on. Multi-view generation is an optional stretch goal only after this flow is dependable.

## 2. Scope and priorities

### P0 — Must work

- Responsive, polished web UI suitable for laptop/tablet demonstration.
- Store catalogue: view products and add a product with image, name, category, price, colour, available sizes, and image type.
- Customer photo upload and camera capture where browser permissions allow.
- Garment selection from the actual catalogue.
- Backend integration with FASHN VTON v1.5.
- Loading, success, and error states for inference.
- Results view showing generated image and selected product details.
- Change the garment and try again using the same session photo.
- Simple catalogue-based recommendations using deterministic filters/matching.
- Temporary handling and cleanup of customer images.
- Setup documentation and a repeatable demo path.

### P1 — Build if P0 is stable

- Neysa Gemma assistant to interpret a natural-language request such as “show me festive options under ₹2,500 in blue or green”.
- Better catalogue search and filters (category, colour, price range, sizes).
- Customer occasion/preferences form.
- Persist a shortlist for the current browser session.

### Stretch only

- Front/side/back captures and multi-angle try-on experimentation.
- Advanced ranking or embeddings for visual similarity.
- Store analytics, inventory integrations, authentication, or cloud storage.

### Explicit non-goals for this event

- True 3D body reconstruction or a real 360° digital twin.
- Guaranteed garment fit, sizing, or measurement estimation.
- Payment, billing, full POS/inventory management, customer accounts, or WhatsApp delivery.
- Training/fine-tuning a VTON model.
- Guaranteed accurate rendering of every Indian garment type.

## 3. Primary user journeys

### Journey A — Store owner adds a garment

1. Store owner opens **Store Catalogue**.
2. Clicks **Add Product**.
3. Uploads a garment photo and enters product details.
4. Selects its category and input-image type:
   - `flat-lay` — garment photographed without a person.
   - `model` — garment photographed on a person/model.
5. Saves the product.
6. The product appears in the catalogue and can be selected for try-on.

For a hackathon demo, seed the app with 8–12 approved/sample products as well as supporting manual upload. Use self-created or properly licensed/consented test images.

### Journey B — Customer tries on a garment

1. Customer opens **Virtual Try-On**.
2. Sees a short privacy note explaining that their image is used to generate a try-on preview.
3. Uploads or captures a full-body, front-facing photo.
4. Sees a preview and can replace the photo before continuing.
5. Selects a garment from the catalogue.
6. Clicks **Try On**.
7. The app shows an explicit processing state while the server runs inference.
8. The completed result is displayed next to the selected product name, price, colour, and sizes.
9. Customer can click **Try Another** to return to the catalogue while keeping the same photo for the current session.
10. Customer can browse suggested alternatives, open one, and try it on.
11. Customer may clear the session to remove the stored customer photo and result images.

### Journey C — Customer asks for recommendations

1. Customer optionally provides occasion, colour preferences, budget, and/or size.
2. The backend filters the actual catalogue using hard constraints (price, availability, category, selected preferences).
3. The app displays a small set of alternatives with a short explanation such as “within budget”, “similar colour”, or “same category”.
4. Customer selects a suggestion to try it on.

Do not show an AI-recommended product that does not exist in the catalogue. Treat price, size, and availability as structured data, not claims invented by the LLM.

## 4. Screens and UI requirements

### Screen 1 — Welcome / Mode selection

- Brand title: **MirrorFit AI** (working name).
- Primary CTA: **Enter Virtual Fitting Room**.
- Secondary CTA: **Manage Store Catalogue**.
- Keep the path into try-on obvious; don't build a marketing landing page that delays the demo.

### Screen 2 — Store Catalogue

- Responsive product grid with image, name, price, category, colour, and available sizes.
- Search and simple filters for category, colour, and price.
- **Add Product** form/modal.
- Show an empty state if no products exist.
- Add basic client/server validation and an understandable upload error state.

### Screen 3 — Customer Photo

- Upload control and camera capture option.
- Accept common image formats: JPEG, PNG, and WebP.
- Validate file type and size on the client and server; choose a sensible documented limit such as 10 MB.
- Explain that a clear, front-facing, full-body image usually works best.
- Show the chosen photo before continuing.
- Provide **Replace Photo** and **Continue** actions.
- Ask for consent before processing the image.

### Screen 4 — Garment Selection

- Display catalogue cards and selected-photo thumbnail.
- Selecting a garment should show its image, price, colour, sizes, and category.
- Primary CTA: **Try On This Outfit**.
- Keep category handling explicit; don't silently map unsupported product types into a different category.

### Screen 5 — Try-On Processing

- Show the selected product thumbnail and a clear loading message, e.g. “Creating your preview…”.
- Prevent accidental duplicate submits while a request is running.
- If inference fails, explain that the preview could not be generated and show **Retry** and **Choose Another Garment** actions.
- Do not display a fake progress percentage.

### Screen 6 — Try-On Result

- Show the generated image prominently.
- Display the selected product's actual name, price, colour, and available sizes.
- Actions: **Try Another**, **View Similar Options**, **Clear Session**.
- Include a small disclaimer: “AI-generated visual preview. Appearance may differ from the physical garment; this does not guarantee fit or size.”
- If result generation is unsuccessful, don't label a sample image as the user's generated result.

### Screen 7 — Recommendations

- Show alternatives from the current catalogue only.
- Each card has actual product image, name, price, and sizes.
- Provide the explanation using known catalogue attributes.
- CTA on every card: **Try This**.

### UI direction

Use a clean, premium retail interface with generous spacing, strong product photography, clear typography, and obvious primary actions. Keep the interface usable on a tablet. Prefer understated neutral backgrounds with one restrained accent colour; don't let animations or decorative UI slow down the primary task. Design loading, empty, error, and success states, not only the happy path.

## 5. FASHN VTON v1.5 integration

### Official project

- GitHub: https://github.com/fashn-AI/fashn-vton-1.5
- Model card: https://huggingface.co/fashn-ai/fashn-vton-1.5
- Release overview: https://fashn.ai/blog/fashn-vton-1-5-open-source-release

### How the model is used

The model receives a person image, a garment image, and a supported garment category. Its documented category values are:

- `tops`
- `bottoms`
- `one-pieces`

It accepts model-worn garment photos and flat-lay product shots, with the garment photo type configured accordingly. Save the source product image as the actual garment input; do not pass a thumbnail if a higher-quality original is available.

For the MVP, begin with common tops and bottoms and test kurta examples explicitly. Treat mapping a kurta to `tops` as a testable assumption. Do not promise accurate saree, lehenga, dupatta, dhoti, layered-outfit, or other unsupported specialized-draping output without validation.

### Suggested model parameters

- `num_samples`: 1 (one output per request for predictable cost/latency).
- `num_timesteps`: start at 20 for a faster test; compare against 30 if quality is insufficient and time permits.
- `segmentation_free`: use the model's documented default unless testing shows a reason to change it.
- `category`: required and must be one of the supported categories.
- `garment_photo_type`: `flat-lay` or `model` according to the uploaded garment image.

Confirm the exact parameters exposed by the installed repository version and follow its example/API; do not invent unsupported arguments.

### Service separation

Implement a dedicated Python service (e.g. FastAPI) for VTON inference. It should:

- Load `TryOnPipeline` once at service startup, not on every request.
- Validate image formats, category, and payload size.
- Convert images to RGB.
- Run inference and save the output under a generated UUID filename.
- Return a result URL or image response through a documented interface.
- Return clear errors for model load failure, invalid inputs, GPU out-of-memory, and inference failure.
- Avoid logging the customer image or raw image contents.

Use the upstream installation/weight-download instructions from the official repository. Keep weights outside version control.

### GPU/runtime warning

The published model card reports approximately 8 GB VRAM for inference and about 5 seconds on an NVIDIA H100; actual latency varies by hardware and settings. Check the available GPU memory before planning local inference. Do not assume a laptop RTX 4050 will have sufficient VRAM. Run a one-image smoke test early. If it fails due to GPU memory or performance, keep the app integration intact and move the VTON service to a confirmed compatible GPU host. Neysa's documented dedicated LLM chat endpoint is not, by itself, evidence that arbitrary FASHN inference can be deployed there.

### License and dependencies

FASHN VTON v1.5 is released under Apache-2.0 according to its project materials, but the project identifies the FASHN Human Parser as a separately licensed third-party dependency. Review that dependency's exact terms before commercial deployment. Include all required attributions and license files; do not assume every dependency shares the main model's licence.

## 6. Suggested architecture

Use the following if the repository has no established stack; otherwise adapt to the existing codebase without unnecessary rewrites.

- **Frontend:** React + Vite + TypeScript.
- **Application backend:** Node.js + Express (or an existing Node framework already in the repo).
- **VTON inference service:** Python + FastAPI + official `fashn-vton-1.5` package.
- **Catalogue database:** SQLite for the prototype.
- **Image storage:** local `uploads/` and `generated/` directories for the demo, with file paths stored in the database. Keep a storage abstraction so it can be replaced later.
- **LLM:** Neysa Gemma only as an optional enhancement after core try-on works; deterministic catalogue matching must function without it.

### Request flow

1. Frontend sends a try-on request to the application backend with the customer's temporary photo and selected `productId`.
2. Backend loads the selected garment image and product category from the catalogue.
3. Backend invokes the VTON service with person image, garment image, category, and garment photo type.
4. VTON service runs FASHN and returns the generated image.
5. Backend stores the generated image under a UUID and returns its result URL plus product metadata.
6. Frontend displays the result and allows trying another catalogue product with the same temporary photo.

Keep the VTON base URL configurable. The Node backend and Python service can run locally during development; if deployed separately, use multipart image transfer or a private object-storage URL rather than relying on shared local file paths.

## 7. Suggested application API

Names can be adapted to the existing code, but implement equivalent behavior and document final routes.

### Catalogue

- `GET /api/products` — list products; support optional `q`, `category`, `colour`, `minPrice`, and `maxPrice` filters.
- `GET /api/products/:id` — get a product and its metadata.
- `POST /api/products` — create a product using multipart form data with product image and metadata.
- `PATCH /api/products/:id` — edit metadata (optional if time is short).
- `DELETE /api/products/:id` — remove a product (optional if time is short).

Suggested product fields:

```json
{
  "id": "uuid",
  "name": "Emerald Cotton Kurta",
  "category": "tops",
  "displayCategory": "Kurta",
  "price": 1499,
  "colour": "green",
  "sizes": ["S", "M", "L"],
  "tags": ["festive", "cotton"],
  "imageUrl": "/uploads/products/<filename>",
  "garmentPhotoType": "flat-lay",
  "available": true
}
```

Store model category (`tops`, `bottoms`, `one-pieces`) separately from display category if needed. This allows the UI to use familiar fashion labels while the model receives only a supported category.

### Try-on

- `POST /api/try-ons` — accept the customer photo plus selected `productId`; return a `tryOnId` and status, or wait for completion if a simple synchronous design is more reliable for the initial build.
- `GET /api/try-ons/:id` — if using asynchronous jobs, return `queued`, `processing`, `completed`, or `failed`, and include `resultImageUrl` when completed.
- `DELETE /api/session` — clear the current session's temporary person photo and generated results.

Example completed response:

```json
{
  "id": "uuid",
  "status": "completed",
  "productId": "uuid",
  "resultImageUrl": "/generated/<filename>.png",
  "createdAt": "ISO-8601 timestamp"
}
```

Choose sync vs. async based on actual inference latency. Do not add a heavyweight queue system for the hackathon. If asynchronous polling is used, an in-memory job map is acceptable for a single-process prototype, with clear failure handling.

### Recommendations

- `GET /api/products/:id/similar` — return other products from the catalogue using deterministic category, colour/tag, and price matching.
- Optional: `POST /api/recommendations` — accept customer preferences such as `occasion`, `budget`, `colours`, and `size`, then return product IDs and explanation strings.

The backend must validate returned product IDs against the current catalogue. If Neysa Gemma is connected, use it to interpret free text or suggest ranking reasons, but enforce all hard filters in application logic. If the LLM fails or is not configured, return deterministic recommendations instead.

## 8. Data model

### Product

- `id` (UUID)
- `name`
- `modelCategory` (`tops`, `bottoms`, `one-pieces`)
- `displayCategory` (e.g. kurta, shirt, trousers, dress)
- `price` (numeric, INR)
- `colour`
- `sizes` (JSON array or related table)
- `tags` (JSON array or related table)
- `imagePath`
- `garmentPhotoType` (`flat-lay` or `model`)
- `available` (boolean)
- `createdAt`, `updatedAt`

### Try-on session/result (minimal)

- `id`
- `productId`
- `resultImagePath` (nullable until complete)
- `status`
- `errorCode`/sanitized `errorMessage` if failed
- `createdAt`
- session identifier or expiry time for cleanup

Do not save a customer's photo into the permanent product catalogue or product database.

## 9. Privacy, safety, and failure handling

- Display a clear consent notice before processing a customer image.
- Use the photo only for the current try-on session; do not use it to identify the customer.
- Do not persist customer photos longer than needed. Delete the temporary person image when the session is cleared and implement an automatic expiry/cleanup path for abandoned sessions.
- Avoid logging image data, image URLs containing secrets, API tokens, or raw personal data.
- Keep generated images temporary too; delete them on session clear/expiry unless the user explicitly saves them.
- Validate uploads on both client and server. Enforce file-size and content-type limits and randomize stored filenames.
- Show a disclaimer that generated images are visual previews and do not guarantee physical fit, size, fabric feel, colour under store lighting, or exact garment details.
- Do not claim unsupported garments work reliably; test the selected sample catalogue.
- On failure, show a clear actionable error. Never silently render an unrelated placeholder as a completed result.

## 11. Acceptance criteria

### Core functionality

- [ ] App starts using documented commands.
- [ ] Catalogue is populated with at least 8 test products or can be populated quickly via upload.
- [ ] User can upload a customer photo and see its preview.
- [ ] User can select a supported product and request a try-on.

- [ ] Clearing/expiring the session removes temporary customer images and session outputs.
- [ ] README documents setup, licences/attribution, environment variables, model constraints, and known limitations.

### Quality bar

- [ ] The main path takes no more than a few clear user actions.
- [ ] No unhandled console errors in the happy path.
- [ ] UI works at laptop and tablet widths.
- [ ] If model inference isn't available in the current environment, the blocker is made explicit and the rest of the frontend/backend can still be tested without misrepresenting the AI result.

## 12. Recommended implementation sequence

1. **Repository and environment check:** inspect files, establish the app runs, verify Python/GPU/VRAM, and test the official FASHN example on one person/garment pair.
2. **Catalogue data and UI:** seed or upload sample items; support browsing and selecting a garment.
3. **Backend VTON adapter:** implement and test the dedicated Python service; keep model loading out of request handlers.
4. **End-to-end try-on flow:** connect photo capture, selected product, inference, result display, and retry/garment switching.
5. **Temporary session cleanup and errors:** add validation, consent copy, deletion, expiry, and safe error states.
6. **Deterministic recommendations:** match alternatives from catalogue data.
7. **Optional Neysa integration:** add natural-language preference parsing only if time remains.
8. **Demo readiness:** test the full flow with the exact catalogue images and person photo planned for the presentation; document fallback steps honestly.

## 13. Demo script

Prepare one consenting/test person image and 3–5 garments that have already been checked for VTON quality.

1. Open the catalogue and show the available products.
2. Upload the person photo.
3. Select a garment and start the try-on.
4. Show the actual generated result and the garment's product details.
5. Select another garment and generate a second result using the same photo.
6. Show the recommendation panel with real catalogue alternatives.
7. Mention that multi-angle try-on is a future experiment, not a completed 360° reconstruction.

Do not run the first model download or first-ever inference for the first time in front of the judges. Pre-download model weights, warm up the service, and rehearse the exact demo path.
